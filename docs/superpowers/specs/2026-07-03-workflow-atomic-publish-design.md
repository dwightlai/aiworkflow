# 工作流设计器原子发布设计

## 目标

在工作流设计器点击“发布”时，一次性保存并发布当前编辑状态，包括：

- 流程名称
- 流程描述
- 节点及节点属性
- 连线及连线条件
- 流程变量
- 画布位置等 UI 配置

发布必须以用户点击按钮时的设计器状态为准，不能发布数据库中的旧草稿。

## 当前问题

设计器当前的发布操作只调用 `POST /api/workflows/{id}/publish`。该接口发布数据库中已经保存的草稿，不会先保存浏览器中的名称、描述和流程定义。

因此，用户修改节点属性或选择多个知识库后直接点击发布时，界面显示发布成功，但新版本仍可能使用旧草稿。

## 方案

采用后端原子发布接口。设计器将名称、描述和完整流程定义随发布请求一起提交，后端在同一事务内完成：

1. 校验流程定义。
2. 更新流程名称和描述。
3. 更新当前草稿定义。
4. 创建并激活新的发布版本。
5. 返回发布后的工作流及版本信息。

任一步骤失败时事务回滚，不产生部分保存或错误发布。

## 接口契约

保留现有接口：

```http
POST /api/workflows/{workflowId}/publish
```

请求体改为可选。设计器提交：

```json
{
  "name": "知识库测试",
  "description": "242345",
  "definition": {
    "nodes": [],
    "edges": [],
    "variables": []
  }
}
```

兼容规则：

- 有请求体：保存请求体中的元数据和定义，然后发布。
- 无请求体：继续发布数据库中的当前草稿，兼容工作流列表页和现有调用方。

## 前端行为

设计器点击发布时：

1. 从设计器实例读取最新定义，而不是依赖可能滞后的 React 状态。
2. 执行完整流程定义校验。
3. 校验通过后调用原子发布接口。
4. 发布期间禁用“保存草稿”“发布”和“运行”操作，避免并发修改。
5. 成功后刷新工作流详情和工作流列表缓存。
6. 失败时保留当前编辑内容，并展示后端返回的错误信息。

新建流程仍需先创建工作流，创建成功进入设计器后才允许发布。

## 后端事务边界

原子发布逻辑放入 `WorkflowApplicationService`，Controller 只负责请求映射。

服务方法在单个事务中调用现有元数据更新、草稿更新和发布能力。事务覆盖工作流主表和工作流版本表，保证发布版本引用的定义与本次请求完全一致。

## 校验与错误处理

- 名称不能为空。
- 定义必须满足现有工作流结构校验规则。
- 工作流不存在或无访问权限时拒绝发布。
- 已归档工作流不得通过设计器直接发布。
- 保存或发布失败时返回明确错误，不返回成功状态。

## 测试标准

后端集成测试：

- 携带完整请求发布后，名称、描述和版本定义全部为请求中的最新值。
- 多知识库节点的 `knowledgeBaseIds` 完整进入发布版本。
- 定义校验失败时，名称、描述、草稿和发布版本均不发生变化。
- 无请求体发布仍兼容原行为。

前端测试：

- 点击发布依次读取最新设计器定义并提交名称、描述和定义。
- 发布请求成功前不显示成功提示。
- 校验失败时不调用发布接口。
- 发布失败时保留编辑状态并显示错误。

## 验收场景

在“知识库测试”流程中选择“档案标准规范”和“企业规章制度”，不单独点击保存草稿，直接点击发布。重新读取最新发布版本时，知识库节点的 `knowledgeBaseIds` 必须包含两个知识库；运行流程时两个知识库都参与候选召回和全局 Top-K 排序。
