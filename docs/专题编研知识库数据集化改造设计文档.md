# 专题编研知识库数据集化改造设计文档

## 1. 设计背景

现有知识库系统已经具备基础 RAG 能力，主要表结构为：

```text
agi_knowledge_base
  └── agi_knowledge_document
        └── agi_knowledge_chunk
              └── agi_knowledge_chunk_vector
```

当前表结构可以支撑普通知识库的文档上传、解析、分块、向量化和检索问答。现有 `agi_knowledge_base` 已包含嵌入模型、向量库配置、分块策略、检索模式、Top-K、文档数、分块数等配置；`agi_knowledge_document` 已包含文档名称、解析状态、原文内容、解析器、分块器、存储路径等字段；`agi_knowledge_chunk` 已包含分块文本、分块序号、启用状态和 token 估算等字段。

随着数字档案馆“专题编研”能力建设，知识库需要支持以下新场景：

1. 数字档案馆中维护专题；
2. 一个专题下存在多类专题资料；
3. 专题资料既可能来自档案系统中的档案，也可能来自数字档案馆中直接录入的外部资料；
4. 知识库系统不维护专题业务数据，只同步数字档案馆专题资料并建立索引；
5. 一个统一的“档案专题编研知识库”下，需要支持多个专题；
6. 每个专题作为一个数据集，用于隔离检索范围；
7. 智能编研基于专题数据集生成大事记、年鉴、专题汇编等成果。

因此，知识库系统需要从原有：

```text
知识库 → 文档 → 分块
```

升级为：

```text
知识库 → 数据集 → 来源索引 → 文档 → 分块 → 向量
```

其中：

- 知识库系统只保存派生索引；
- 数字档案馆仍是专题资料主库；
- 档案业务系统仍是档案业务主库；
- 知识库通过 `source_ref_id` 回溯数字档案馆专题资料；
- 如果专题资料来自档案，再通过 `source_archive_file_id` 回溯原档案；
- 知识库通过 `metadata_json / metadata_snapshot` 保存同步时的元数据快照，用于检索过滤、引用展示和索引判断。

### 已实现（P1）

| 能力 | 说明 |

## 2. 改造目标

### 2.1 业务目标

1. 支持一个知识库下多个**分类**（含默认分类、手动分类、专题同步分类）；
2. 支持每个专题（topicId）对应一个 `ARCHIVE_TOPIC` 分类（由开放接口 sync 创建）；
3. 支持从数字档案馆**推送**专题资料（开放接口，非管理端拉取）；
4. 支持专题资料来源多样化，包括档案、外部录入文本、上传文件、图片、结构化数据等；
5. 支持按分类（`dataset_id`）进行独立检索；
6. 支持基于分类的智能编研（`compile/from-knowledge-dataset`）；
7. 支持引用来源回溯；
8. 不修改数字档案馆和档案业务库的数据结构。

### 2.2 技术目标

1. 保持原有知识库表结构兼容；
2. 新增 `agi_knowledge_dataset` 表；
3. 新增 `agi_knowledge_source_index` 表；
4. 扩展 `agi_knowledge_document`；
5. 扩展 `agi_knowledge_chunk`；
6. 向量库索引中增加 `dataset_id`、`topic_id`、`source_ref_id` 等 metadata；
7. ~~普通知识库使用单数据集模式，用户无感知~~（**已实现调整**：所有知识库统一多分类能力，管理端以「分类」呈现，默认分类承载未归类文档）；
8. 专题资料通过开放接口同步，每个专题可对应一个 `ARCHIVE_TOPIC` 分类（亦支持手动建分类）。

#### 向量库保存

```text

```

逻辑上表示分块向量索引，实际可以落在：

1. ES8 / OpenSearch；
2. Milvus；
3. PostgreSQL + pgvector；
4. 其他向量数据库。

向量库中建议保存：


## 4. 核心设计原则

### 4.1 数字档案馆是专题资料主库

数字档案馆负责维护：

```text
专题
专题资料
资料来源类型
关联档案
外部录入资料
上传资料
专题分类
排序
是否参与编研
密级
业务权限
```

知识库系统不重复维护这些业务关系。

### 4.2 知识库是专题资料索引库

知识库系统只负责：

```text
同步专题资料
保存同步索引记录
解析正文
切分 chunk
生成 embedding
抽取事件
抽取结构化记录
提供检索服务
```

### 4.3 source_ref_id 指向数字档案馆专题资料

知识库侧统一认为所有同步对象都是数字档案馆的“专题资料”。

```text
source_ref_id = 数字档案馆专题资料 ID
```

如果这条专题资料来自档案，则额外保存：

```text
source_archive_file_id = 原档案 ID
```

这样可以同时支持：

```text
专题资料 → 回溯专题资料详情
专题资料 → 如果来自档案，再回溯原档案
```

### 4.4 metadata_snapshot 是同步快照，不是业务主数据

知识库保存的 `metadata_snapshot / metadata_json` 是数字档案馆同步过来的元数据快照，用于：

1. 检索过滤；
2. 引用展示；
3. 权限过滤；
4. 判断是否需要重建索引；
5. 编研成果生成。

正式业务数据仍以数字档案馆和档案业务系统为准。

## 5. 知识库模式设计

> **已实现调整（2026-06）**：原「SINGLE 用户无感 / MULTI 专题专用」双模式已合并为**统一多分类模型**。下文保留原设计意图供后续演进参考；当前产品行为以 **5.4** 为准。

### 5.1 单数据集模式（原设计，未作为独立产品形态落地）

适用于希望完全隐藏分类层的场景（**当前未实现 UI 隐藏**）。

```text
知识库：公司制度知识库
└── 默认分类（DEFAULT）
    ├── 员工手册
    ├── 财务制度
    └── 信息安全制度
```

原设计特点：前端不显示分类、自动默认分类、检索限定默认分类。**现状**：分类树对所有知识库可见，默认分类仅表示「未归入其他分类的文档」。

### 5.2 多数据集模式（专题同步场景）

适用于专题编研：一个专题对应一个 `ARCHIVE_TOPIC` 分类（由开放接口同步时 `findOrCreateTopicDataset` 创建）。

```text
知识库：档案专题编研知识库
├── 默认分类（DEFAULT，系统创建，不可删改）
├── 分类：H-100智能制造一号厂房建设纪实   ← topicId 绑定
├── 分类：档案数字化建设专题
└── 分类：2025年度档案工作年鉴
```

### 5.3 base 表模式字段

`agi_knowledge_base` 已增加：

```text
kb_type
biz_scope
dataset_mode
default_dataset_id
dataset_count
metadata_json
```

| 字段 | 设计取值 | 当前实现 |
|------|----------|----------|
| `dataset_mode` | `SINGLE` / `MULTI` | 创建与 `ensureDefaultDataset` **固定 `MULTI`** |
| `kb_type` | `NORMAL` / `ARCHIVE_TOPIC` 等 | 管理端不展示；创建时写 `NORMAL` |
| `biz_scope` | 业务域 | 未使用，恒为 null |

### 5.4 统一多分类模型（当前实现）

```text
任意知识库
├── 默认分类（DEFAULT，自动创建，不可编辑/删除）
├── 手动分类（MANUAL，管理端「新建分类」）
└── 专题分类（ARCHIVE_TOPIC，开放接口 sync 时按 topicId 创建或复用）
```

规则：

1. 新建知识库 → 自动创建默认分类，写入 `default_dataset_id`，`dataset_count` 初始为 1；
2. 用户可随时「新建分类」，无需区分知识库类型；
3. 文档上传/手动入库可带 `datasetId`；未传则解析为 `default_dataset_id`；
4. 默认分类不可编辑名称（前端展示为「默认分类」）、不可删除；
5. 数字档案馆专题资料**不在管理端维护**，仅通过开放接口 `sync` 推送；
6. 管理端文案使用「**分类**」，与后端 `dataset` 实体一一对应。

**管理端无此接口。** 数字档案馆（或已授权的第三方应用）调用：

```http
POST /api/open/knowledge-bases/{kbId}/archive-topics/{topicId}/sync
```

鉴权：集成应用 scope `SCOPE_KNOWLEDGE_BASE` 须包含目标 `kbId`。

请求体由调用方携带专题标题、资料列表（`sourceRefId`、`sourceVersion`、`title`、`materialSourceType`、`contentText`、`metadata` 等），**不是**由知识库再去拉取数字档案馆 HTTP 接口。

~~原设计 Admin 路径~~：

```http

```

**未实现**，保留为后续可选能力。

#### 7.3.2 处理流程

```text
接收 topicId
        ↓
调用数字档案馆接口获取专题详情
        ↓
查询或创建 agi_knowledge_dataset
        ↓
调用数字档案馆接口获取专题资料列表
        ↓
逐条 upsert agi_knowledge_source_index
        ↓
对新增或变更资料创建索引任务
        ↓
更新 dataset 统计与状态
```

#### 7.3.3 变更判断

根据以下字段判断是否需要重新索引：

```text
source_ref_id
source_version
metadata_snapshot
source_title_snapshot
```

如果数字档案馆返回的 `source_version` 大于知识库中的 `source_version`：

```text
index_status = STALE
```

然后进入重建索引流程。

### 7.4 专题资料索引逻辑

#### 7.4.1 输入

`agi_knowledge_source_index` 一条记录。

#### 7.4.2 流程

```text
读取 source_index
        ↓
根据 material_source_type 获取正文
        ↓
ARCHIVE_FILE：调用数字档案馆/档案系统获取 OCR 文本或文件
MANUAL_TEXT：读取数字档案馆返回的 content
UPLOAD_FILE：下载文件并解析
STRUCTURED_DATA：转换为文本和结构化记录
EVENT_RECORD：写入事件表并生成文本
        ↓
创建或更新 agi_knowledge_document
        ↓
解析文本 raw_content
        ↓
生成摘要 summary_text
        ↓
切分 chunk
        ↓
写入 agi_knowledge_chunk
        ↓
调用 embedding 服务生成向量
        ↓
写入向量库
        ↓
可选：抽取事件 / 结构化记录
        ↓
更新 index_status = READY
```

#### 7.4.3 material_source_type 处理策略

| 类型 | 处理方式 |
|---|---|
| `ARCHIVE_FILE` | 优先获取档案 OCR 文本；没有则下载原文解析 |
| `MANUAL_TEXT` | 直接使用文本内容 |
| `UPLOAD_FILE` | 根据文件类型调用解析器 |
| `WEB_LINK` | 读取网页正文，必要时缓存快照 |
| `IMAGE` | OCR + 图片说明 |
| `STRUCTURED_DATA` | 保存结构化记录，生成文本摘要 |
| `EVENT_RECORD` | 写入事件表，生成事件 chunk |

### 7.5 删除与失效处理

知识库系统不主动删除数字档案馆业务数据。

当数字档案馆删除或移除专题资料时，同步接口应返回资料状态，知识库侧处理为：

```text
source_index.index_status = DISABLED
document.enabled = false
chunk.enabled = false
向量库删除或标记 disabled
```

推荐逻辑删除，不建议物理删除，便于审计和问题追踪。

## 15. 总结

本次改造的核心不是把数字档案馆专题资料搬到知识库里重新维护，而是让知识库成为数字档案馆专题资料的**索引服务**；管理端侧重**分类 + 文档**维护，专题资料**推送同步**走开放接口。

**当前已落地结构：**

```text
agi_knowledge_base
  └── agi_knowledge_dataset（管理端称「分类」）
        ├── DEFAULT 默认分类
        ├── MANUAL 手动分类
        └── ARCHIVE_TOPIC 专题同步分类
              └── agi_knowledge_source_index（同步 / 手动文本资料）
                    └── agi_knowledge_document
                          └── agi_knowledge_chunk
                                └── 向量索引（含 dataset_id）
```

**核心原则（修订后）：**

```text
数字档案馆维护专题资料；知识库通过开放接口接收同步并建索引；
source_ref_id 指向数字档案馆专题资料；
source_archive_file_id 仅在资料来自档案时有值；
metadata_snapshot 保存同步快照；
dataset_id（分类）用于检索隔离与编研范围；
所有知识库均有默认分类，并可随时新建分类；
专题同步不在管理端操作，由数字档案馆调用 Open API；
事件/结构化层、密级过滤、分类级权限为后续分期能力。
```
