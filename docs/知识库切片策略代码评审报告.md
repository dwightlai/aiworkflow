# 知识库切片策略代码评审报告

> 评审范围：`server/src/main/java/com/mw/ai/agi/knowledge/chunking/*` 与 `knowledge/service/*` 切片相关实现
> 评审性质：只读评审，未修改任何代码
> 评审日期：2026-07-02

---

## 一、架构总览

当前切片系统由四层组成：

1. **入口层** `KnowledgeDocumentSplitter` —— 根据文件名选择解析器，根据 splitterType 选择走"结构化路径"还是"文本路径"
2. **文档解析层** `StructuredDocumentParser`（Markdown / Office / Csv / PlainText）—— 将原始文本解析为 `DocumentStructure`（含 `DocumentNode` 列表）
3. **策略路由层** `DefaultChunkStrategyRouter` —— 先聚合小表格行与短章节，再分发给 `NodeChunkStrategy`
4. **节点切片层** `DefaultNodeChunkStrategy` —— 按节点类型决定原子切片或句子边界切片

辅助组件：`HeuristicTokenCounter`（token 估算）、`SemanticBoundaryChunker`（基于嵌入的语义切分）、`KnowledgeSplitter`（旧版字符切片）、`ChunkProfileService`（配置版本管理与 A/B 对比）。

---

## 二、问题清单（按严重程度分级）

### 🔴 P0 严重问题

#### P0-1 度量单位混乱：Token 与字符长度混用

**位置**：
- `DefaultNodeChunkStrategy` / `DefaultChunkStrategyRouter` / `SemanticBoundaryChunker` 使用 `tokenCounter.count()`（token 数）
- `KnowledgeDocumentSplitter.splitFixed/splitParagraph/splitSentenceBoundary/splitSymbol/splitTableRows` 使用 `content.length()`（字符长度）
- `KnowledgeSplitter`（旧版）用 `length() / 4.0` 估算 token

**现象**：同一个 `chunkSize` 参数在不同路径下语义完全不同。用户配置 `chunkSize=800`：
- 走 STRUCTURE_AWARE → 800 被当作 token 上限（CJK 约 800 字）
- 走 PARAGRAPH / FIXED_LENGTH → 800 被当作字符数（约 800 字符）

**影响**：切片大小不可控、不可预测。切换 splitterType 会导致切片粒度突变，且 `KnowledgeSplitRequest.effectiveChunkSize()` 默认返回 200（字符），而 `ChunkProfile.defaults()` 默认 800（token），两者根本不是一个量纲。

---

#### P0-2 `ChunkProfile.defaults()` 丢弃用户配置的 chunkSize

**位置**：`ChunkProfile.java` 第 28-43 行

```java
public static ChunkProfile defaults(String strategy, int chunkSize, int overlap) {
    int max = chunkSize <= 0 ? 800 : chunkSize;
    return new ChunkProfile(
            strategy,
            Math.min(500, max),          // ← targetTokens 强制不超过 500
            max,
            Math.min(120, Math.max(0, max / 4)),  // ← minTokens 硬编码上限 120
            overlap,
            ...
    );
}
```

**现象**：即使用户配置 `chunkSize=1000`，`targetTokens` 会被 `Math.min(500, 1000)` 压成 500；`minTokens` 被强制压到 120。用户配置的 size 参数在结构化路径里基本不生效（只有 `maxTokens` 在"是否需要二次切句子"时生效）。

**影响**：`ChunkProfileService` 提供的 A/B 对比功能里，用户调整 chunkSize 看不到预期变化，调参失真。

---

#### P0-3 overlap 配置在结构化路径中完全失效

**位置**：`DefaultNodeChunkStrategy.splitAtSentenceBoundaries()` 第 68-94 行

**现象**：`ChunkProfile` 有 `overlapTokens` 字段，但 `splitAtSentenceBoundaries` 按句子边界切完后**相邻 chunk 之间没有任何重叠窗口**。切完即切完。

**影响**：结构化切片号称支持 overlap，实际未实现。召回时跨 chunk 边界的信息会丢失（一个完整语义被切成两段，检索只能命中其一）。`overlapTokens` 仅在旧版 `KnowledgeSplitter` 和 `splitFixed`（FIXED_LENGTH 路径）里生效。

---

### 🟠 P1 中等问题

#### P1-1 parentId 用 String.hashCode 生成，存在碰撞且父 chunk 从未创建

**位置**：`DefaultNodeChunkStrategy.parentId()` 第 96-99 行

```java
String key = document.documentTitle() + "|" + String.join("/", node.sectionPath());
return "parent_" + Integer.toUnsignedString(key.hashCode(), 36);
```

**问题**：
1. `String.hashCode()` 是 32 位，不同章节路径可能碰撞 → 父子关系错乱
2. **父 chunk 本身从未被创建**。`DefaultChunkStrategyRouter` 只遍历非 TITLE/DOCUMENT 节点生成 CHILD chunk，没有生成对应的 PARENT 摘要 chunk。`createParentChunks=true` 配了但没人用，`parentCoverageRatio` 依赖的父 ID 永远是虚拟的

---

#### P1-2 ChunkProfile 多个配置项是死代码

**位置**：`ChunkProfile` 字段 vs `DefaultNodeChunkStrategy` / `DefaultChunkStrategyRouter` 实现

| 配置字段 | 是否被读取 | 实际行为 |
|---|---|---|
| `createParentChunks` | ❌ 未读取 | 从不生成父 chunk |
| `createChildChunks` | ❌ 未读取 | 总是生成 child |
| `neighborWindow` | ❌ 未读取 | 无邻居上下文扩展 |
| `preserveAtomicBlocks` | ❌ 未读取 | atomic 判断硬编码在 strategy |
| `includeSectionPath` | ❌ 未读取 | 总是包含 |

**影响**：配置项给用户错觉，实际不生效。调参无响应。

---

#### P1-3 句子切分正则覆盖不全，且超长句子不二次切分

**位置**：`DefaultNodeChunkStrategy.splitAtSentenceBoundaries()`、`SemanticBoundaryChunker.sentences()`、`KnowledgeDocumentSplitter.splitSentenceBoundary()`

```java
text.split("(?<=[。！？.!?])\\s*")
```

**问题**：
1. 只识别 `。！？.!?`，不识别中文分号 `；`、冒号 `：`、换行符
2. 编号 `1. 2. 3.` 中的点会被误判为句号边界
3. 当单个句子本身超过 `maxTokens` 时，`splitAtSentenceBoundaries` 直接把整个超长句子作为一个 chunk 放进去（第 85 行 `chunks.add(value)`），**没有进一步按字符/子句切分**，导致 maxTokens 被突破

---

#### P1-4 SemanticBoundaryChunker 的 topicShift 逻辑有缺陷

**位置**：`SemanticBoundaryChunker.java` 第 41-43 行

```java
boolean topicShift = index > 0
        && sentenceCount >= 2
        && cosineSimilarity(vectors.get(index - 1), vectors.get(index)) < DEFAULT_SIMILARITY_THRESHOLD;
```

**问题**：
1. 只比较**相邻两个句子**的相似度。真正的语义边界检测应比较"前面累积块的平均向量"与"当前句子"，而不是相邻两句。相邻两句即使主题不变，也可能因指代、转折而相似度低，造成误切
2. 阈值 0.78 硬编码，不可配置
3. `embedAll` 对所有句子一次性嵌入，大文档会触发限流/超时，没有分批和缓存
4. topicShift 触发时**不考虑当前块是否太小**，可能产生极小 chunk（2 句话就切）

---

#### P1-5 `KnowledgeDocumentSplitter(KnowledgeSplitter)` 兼容构造函数绕过真实 EmbeddingClient

**位置**：`KnowledgeDocumentSplitter.java` 第 42-54 行

```java
public KnowledgeDocumentSplitter(KnowledgeSplitter legacyEstimator) {
    this(
            ...,
            new SemanticBoundaryChunker(new LocalEmbeddingClient(), ...)  // ← 本地假实现
    );
}
```

**问题**：这个构造函数内部 `new LocalEmbeddingClient()`，创建一个不被 Spring 管理的本地嵌入客户端，绕过了用户配置的真实 `EmbeddingClient`（如 `ModelProviderEmbeddingClient`）。若走 SEMANTIC 路径，用的是 LocalEmbeddingClient（可能是哈希模拟），语义切分结果失真。

---

#### P1-6 CsvStructureParser 不处理引号转义

**位置**：`CsvStructureParser.java` 第 63-65 行

```java
private List<String> split(String line) {
    return Arrays.stream(line.split(",", -1)).map(String::trim).toList();
}
```

**问题**：标准 CSV 字段可能用双引号包裹、内部含逗号或换行。直接按逗号 split，遇到 `"a,b",c` 会切错。而 `OfficeStructureParser.parseMarkdownRow` 反而实现了转义逻辑，两者处理方式不一致。

---

#### P1-7 OfficeStructureParser 强依赖 Markdown 解析，无降级

**位置**：`OfficeStructureParser.java` 第 29-30 行

```java
private final MarkdownStructureParser markdownParser = new MarkdownStructureParser();
public DocumentStructure parse(String fileName, String content) {
    DocumentStructure markdown = markdownParser.parse(fileName + ".md", content);
    ...
}
```

**问题**：Office 文档的 `content` 参数是上游 `DocumentTextExtractor` 转换后的 Markdown 文本。切片质量**完全依赖前置提取器输出 Markdown 的质量**。若提取器没把 docx 标题转成 `#`、没把表格转成 Markdown 表格，结构化解析全部失效，退化为按段落切。这是一种隐式耦合，且没有对"提取结果不是有效 Markdown"的情况做降级处理或告警。

---

### 🟡 P2 次要问题

#### P2-1 aggregateShortSections 合并可能跨语义，且丢失原节点元数据

**位置**：`DefaultChunkStrategyRouter.aggregateShortSections()` 第 103-135 行

合并只看 `sectionPath` 相同和 token 数，不看内容语义。两个同章节但讨论不同子话题的短段落会被强制合并，用 `\n` 连接。合并后 `metadata` 只保留 `aggregated=true, sourceNodeCount`，原节点的元数据全部丢失。

---

#### P2-2 PlainTextStructureParser 的 sectionPath 永远为空，导致短段落永不聚合

**位置**：`PlainTextStructureParser.java` 第 30-41 行

纯文本节点 `sectionPath` 硬编码 `List.of()`。而 `aggregateShortSections.isShortSectionContent()` 要求 `!node.sectionPath().isEmpty()`，所以纯文本的短段落**永远不进入聚合逻辑**，即使未达到 minTokens。

---

#### P2-3 KnowledgeSplitter 与 KnowledgeDocumentSplitter 双轨并存（技术债）

存在两个 splitter：`KnowledgeSplitter`（旧版，字符长度，3 参数）与 `KnowledgeDocumentSplitter`（新版，结构化 + token，5 参数）。职责重叠，维护成本高，且容易调错。

---

#### P2-4 缺少切片质量门禁闭环

`ChunkingQualityReport` 能算出 minTokens/maxTokens/atomicRatio，但没有在切片入库流程里做**自动质量校验**：比如发现 maxTokens 远超阈值时自动触发二次切分，或 atomicRatio 过低时告警。质量报告只用于 Profile 对比预览，入库时不校验。

---

#### P2-5 表格行 rowIndex 与实际数据行序号不一致

**位置**：`OfficeStructureParser.expandTableRows()` 第 64-98 行

`rowIndex` 存的是原始 Markdown 行号（从 2 开始，跳过分隔行），而非数据行的逻辑序号。后续如需按行定位会混淆。

---

## 三、改进方向建议（不修改代码，仅作参考）

1. **统一度量单位**：全部走 token 计数，废除字符长度路径；或显式区分 `chunkSizeTokens` 与 `chunkSizeChars` 两个参数
2. **修复 `defaults()`**：尊重用户配置的 chunkSize 作为 targetTokens，minTokens 按比例推导而非硬编码上限
3. **实现 overlap**：在 `splitAtSentenceBoundaries` 中引入滑动窗口，保留前 N 个句子作为重叠
4. **生成真正的父 chunk**：对每个 sectionPath 生成摘要型 PARENT chunk，或用 LLM 生成章节摘要
5. **清理死配置**：要么实现 `createParentChunks/neighborWindow` 等，要么从 ChunkProfile 删除
6. **增强句子切分**：加入 `；：` 和换行作为软边界；超长句子回退到字符级切分
7. **改进语义切分**：用累积块平均向量做比较；阈值可配置；嵌入分批+缓存
8. **CSV 引号处理**：统一使用支持 RFC 4180 的解析（如 opencsv），或复用 OfficeStructureParser 的转义逻辑
9. **Office 解析降级**：检测提取结果是否含 Markdown 结构标记，若无则告警并降级为纯文本切分
10. **统一 splitter**：废弃 `KnowledgeSplitter`，全部走 `KnowledgeDocumentSplitter`

---

## 四、总体评价

当前实现**架构思路是清晰的**（结构感知 + 原子块保护 + 短章节聚合 + 配置版本管理 + A/B 对比），方向正确。但存在三类系统性问题：

1. **配置与实现脱节**：大量配置项不生效（P0-2、P1-1、P1-2），用户调参失真
2. **度量单位不统一**：token 与字符混用（P0-1），切片粒度不可预测
3. **关键能力缺失**：overlap 未实现、父 chunk 未生成、超长句子不二次切分

建议优先修复 P0 三项（单位统一、defaults 尊重配置、overlap 实现），这是切片质量可控的基础。P1 中的语义切分逻辑和 CSV 解析属于正确性缺陷，建议随后处理。
